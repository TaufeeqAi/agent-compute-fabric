# Client conformance suite

`scenarios.json` is the acceptance test of any client of the public API. Each scenario scripts what a
server answers and states what a correct client does. The Python SDK, the TypeScript SDK and the `acf`
command-line client each run every scenario; a client written by anyone else is offered the same file.

The suite tests the client protocol, which is what keeps one idempotency key equal to one operation
when answers are lost:

| Rule | A client |
|---|---|
| CP-1 | uses one idempotency key per intent, created before the first attempt and kept across every retry |
| CP-2 | resolves a lost answer, `OUTCOME_UNRESOLVED` and `REQUEST_IN_PROGRESS` by repeating the same request with the same key and the same body, and never uses a new key to get past them |
| CP-3 | decides from `kind`, `code` and `retry`, never from the HTTP status alone and never from message text |
| CP-4 | follows an operation to a state in which it has ended, or reports that it is still running; a state it does not know is neither terminal nor success |
| CP-5 | never shows `UNKNOWN` or `OUTCOME_LOST` as success or as failure |

## Format

```text
{
  "schema_version": 1,
  "defaults": { "project": "...", "base_url": "...", "api_key": "..." },
  "scenarios": [ Scenario, ... ]
}

Scenario = {
  "id":        unique, stable
  "title":     one sentence
  "rules":     [ "CP-2", "SDK-5", ... ]            the clauses the scenario proves
  "call":      { "name": Call, "args": { ... } }   the one logical call the client makes
  "config":    { "max_retries": 2, ... }           optional client settings for this scenario
  "exchanges": [ Exchange, ... ]                   what the server sees and answers, in order
  "expect":    Expectation
}

Exchange = {
  "request":  { "method", "path", "query"?, "headers"?, "json"? }
  "response": { "status", "headers"?, "json"? }   or   { "fault": "connection_reset" | "timeout" }
}

Expectation = {
  "outcome":   "success" | "error"
  "error":     { "class", "code"?, "kind"?, "retry"? }      when outcome is "error"
  "result":    { ... }                                      a subset the result must contain, when "success"
  "replayed":  true | false                                 optional
  "exit_code": Exit                                         the exit class of the command-line client
  "min_wait_s": number                                      optional: the client waited at least this long, in total
}
```

Matching rules for a runner:

- The client's requests must arrive in the order of `exchanges`, one per exchange, and no request may
  be left unanswered or unexpected.
- `method` and `path` must be equal. `query` and `headers` are subsets: every member listed must be
  present and equal (header names compared without case). `json`, when given, must equal the body.
- `"$KEY"` in a header or body stands for the idempotency key of the call: the value given in
  `call.args.idempotency_key`, or, when the call gives none, whatever key the client generated for its
  first attempt. `"$KEY:start"` and `"$KEY:destroy"` are that key with the suffix: the keys of the start,
  and of the clean-up after a start that did not succeed, which `sandbox.create` issues after the create.
- A `fault` happens after the request has been received: the client gets no response.
- A runner replaces the client's clock and sleep with virtual ones. No scenario waits in real time.

`Call` names are neutral, and each client maps them onto its own surface:
`sandbox.create`, `sandbox.get`, `sandbox.list`, `sandbox.start`, `sandbox.exec`, `sandbox.stop`,
`sandbox.destroy`, `sandbox.snapshot`, `snapshot.restore`, `snapshot.delete`, `snapshot.list`,
`execution.get`, `execution.output`, `execution.cancel`, `operation.get`, `auth.whoami`, `info`.

`Exit` names the exit class of the command-line client, not a number:
`success`, `command_failed` (the operation succeeded and the command it ran exited with a status other
than 0), `usage`, `refused`, `operation_failed`, `outcome_unknown`, `unreachable`, `unresolved`,
`outcome_lost`, `still_running`.

Error classes are the names in `../api/problems/registry.yaml` (`sdk_exception`), with four that no
problem document carries: `OperationFailedError` (an operation ended `FAILED` or `CANCELLED`),
`OutcomeUnknownError` (it ended `UNKNOWN`, or `FAILED`/`CANCELLED` with effect `MAY_BE_APPLIED`),
`OperationStillRunningError` (the follow bound was reached) and `APIConnectionError` (the server could
not be reached and nothing can be said).

`scenarios.json` is generated by `acf_api.artifacts.conformance` (`make platform-artifacts`), which builds
each answer from the public model, so that an answer in this file is one the platform can give. Edit the
generator, not the file.

## Following an operation

Every client follows an operation the same way, so that the requests of a scenario are determined:

0. The server holds a mutation open until its operation has ended, for up to its own wait: 30 seconds
   unless the request says otherwise. A mutation whose follow bound is shorter than 30 seconds therefore
   carries `wait` = the whole seconds of the bound, so that the bound is not spent, and overrun, waiting
   for the first answer; a bound of zero submits and returns at once. Any other mutation carries no
   `wait`. The bound itself counts from the answer that first shows the operation.
1. After an answer in which the operation has not ended, wait `Retry-After` seconds if the answer carried
   the header, else the backoff (0.5 s, doubling, capped at 5 s).
2. If that wait would reach the follow bound, stop and report the operation as still running.
3. Otherwise read the operation with `wait` = the smaller of 30 and the whole seconds left before the bound.

## Bodies

A client sends the required members of a body and the members its caller set. It sends no member whose
value is null, and it does not spell out a default the caller did not ask for. The platform fills defaults
before it computes the fingerprint of a request, so two bodies that differ only in a spelled-out default
are the same request.
